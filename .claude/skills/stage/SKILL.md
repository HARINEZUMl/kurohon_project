# 段階を一つ進める

対象: $ARGUMENTS

以下の手順で進める。順序を入れ替えない。

## 1. 読む

- `SPEC.md` の該当節を読む。要約や記憶で判断しない
- `CLAUDE.md` の「処理の順序」で、この段階の前後の依存を確認する
- **前段が未実装なら、ここで止めて報告する。** 依存先が無いまま先へ進むと
  土台を入れ替える手戻りになる

## 2. 方針を述べて止まる

実装を書く前に、次を述べて確認を取る。

- SPEC のどの規定をどう実装するか
- 仕様に書かれておらず判断が必要な箇所（あれば必ず挙げる）
- 回帰テストで何を検証するか

承認を得るまでコードを書かない。

## 3. 実装する

- モジュールは `CLAUDE.md` のファイル構成に従う。既存モジュールの役割を混ぜない
- 確定できないものは「確定不能」として記録する。もっともらしい値を入れない
- 仕様の穴を推測で埋めない。必要になったら止めて報告する

## 4. 回帰テストを書く

`tests/` に置く。対象は狭く取る。

| 段階 | 起点ページ |
|---|---|
| 抽出・領域分割・木の構築 | p200 |
| 管制用語・波括弧 | p158 |
| 用例・ページまたぎ | p302〜p303 |
| 参照解決 | p254 |
| 多重併記・第8段 | p245 |

384ページ全体を対象とするテストを書かない。PostToolUse フックの
タイムアウト（150秒）に掛かる。

## 5. 点検を受ける

diff-checker サブエージェントに委譲する。自分で点検しない。

指摘があれば直し、直したら再度委譲する。指摘が消えるまで繰り返す。

diff-checker が「spec-reviewer に回すべき」とした項目は、自分で判断せず
報告に残す。

## 6. 報告する

`CLAUDE.md`「報告の仕方」に従い、次を書く。

- 何を変更したか
- 検証の数値が前回からどう変化したか（悪化した項目を必ず含める）
- 判断に迷った箇所と、どう処理したか
- 仕様に書かれていないために推測が必要だった箇所

あわせて、diff-checker が spec-reviewer に回すとした論点を列挙する。

## 守ること

- 検証を通すために判定を緩めない。不一致の原因は実装にある
- 検証の数値が悪化したら、原因を報告して止まる。先に進まない
- `SPEC.md` を編集しない
- DECISIONS.md は追記のみ。既存の記録を書き換えない
